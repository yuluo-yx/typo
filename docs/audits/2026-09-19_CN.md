## 已确认的问题

### F01：并发写入规则和历史丢失已成功提交的数据

**触发条件：** 多个终端或进程同时调用 `typo learn`，或同时执行会记录历史的 `typo fix`。

**复现与结果：** 在独立目录中提交 40 条不同规则，用 16 个工作线程启动独立 CLI 进程。所有进程退出码都是 `0`，最终 `rules.json` 只有 4 条。使用 40 个不同的 `gti status -- audit<N>` 输入测试历史，所有修正成功，`usage_history.json` 只有 3 条。串行对照组分别保留全部 40 条。具体丢失数量取决于进程调度。

**原因与定位：** `internal/engine/rules.go:106`、`internal/engine/rules.go:488` 和 `internal/engine/history.go:44`、`internal/engine/history.go:293` 仅使用实例内互斥锁。每个进程加载自己的旧快照，再整文件写回；原子重命名保证单次文件替换完整，不能合并并发更新。

**影响：** 成功提示与最终持久化结果不一致，个人规则和使用历史静默丢失。`go test -race` 检查同一进程的内存竞争，因此通过 race 检查不能排除此问题。

**建议及验收：** 将跨进程互斥、重新读取、修改、写回纳入同一事务，覆盖规则及历史写入入口。验收时要求 40 次并发成功操作全部持久化，再检查同一历史项计数及自动学习流程。本次未修复，也未把配置、缓存的类似代码推断列为已实测缺陷。

### F02：Bash 等待 stderr 收集进程，导致后台任务阻塞提示符

**触发条件：** 加载 Bash 集成后，后台子进程继续持有继承的 stderr，例如 `sleep 2 &`。

**复现与结果：** 在隔离 Bash 中按真实钩子顺序调用 `_typo_preexec`、启动后台任务、调用 `_typo_precmd`，测量第一条提示符标记到达时间。未加载集成时，Bash 3.2/5.2 分别约 3/4 ms；加载集成后分别为 2.030/2.036 s。

计时针对提示符标记，而非整个子进程退出时间；避免把后台任务持有测试管道造成的等待误判为提示符阻塞。

**原因与定位：** `install/typo.bash:459` 将 stderr 重定向到 FIFO；`install/typo.bash:488` 无超时地 `wait` 收集进程。后台任务持有 FIFO 写端，收集进程在任务结束之前收不到 EOF。

**影响：** 后台任务失去立即返回提示符的体验；等待时间随后台任务持续时间增长。这一增长关系来自管道生命周期，实测任务长度为 2 s。

**建议及验收：** 调整收集进程生命周期，使提示符不依赖所有后台 stderr 写端关闭。验收需要同时检查后台任务立即返回提示符、前台错误输出、连续命令隔离和退出清理。当前测试为钩子集成测试，未做真实终端按键自动化。

### F03：环境变量修正不识别当前命令内的变量定义

**触发条件：** Shell 上下文导出 `HOME`，当前输入定义了相似但合法的局部变量 `HOEM`。

```bash
HOEM=/tmp; echo "$HOEM"
for HOEM in /tmp; do echo "$HOEM"; done
```

**复现与结果：** 通过 `--alias-context` 提供 `HOME` 环境变量名后，两条命令的读取端均被改成 `$HOME`，定义端保留 `HOEM`。在隔离 Bash 中执行原命令输出 `/tmp`，执行修正结果输出测试 HOME 路径。无局部定义的 `echo $HOEM` 对照组仍能正确改成 `echo $HOME`。

**原因与定位：** `internal/engine/env_context.go:23` 按上下文中的环境变量名匹配引用，遍历 `line.args`，没有收集赋值语句或循环变量的定义和作用域。

**影响：** 本来合法的命令被改成另一种含义。问题不局限于漏修拼写错误。

**建议及验收：** 识别当前命令内的变量绑定，并对不能确定作用域的引用采取保守策略。回归至少覆盖赋值、循环、函数内局部变量以及未定义变量的正常修正。本次直接验证了赋值和循环两种形态。

### F04：Bash 集成改变已有提示符与退出钩子的状态值

**触发条件：** 用户已有读取 `$?` 的 `PROMPT_COMMAND` 或 `EXIT` trap，再加载 Typo 集成。

**复现与结果：** 两版 Bash 的对照结果一致：

| 场景 | 未加载 Typo | 加载 Typo |
| --- | --- | --- |
| `false` 后，原 `PROMPT_COMMAND` 读取 `$?` | `1` | `0` |
| `exit 7` 时，原 EXIT trap 读取 `$?` | `7` | `0` |

Shell 进程自身仍以 `7` 退出；已证实被破坏的是原钩子收到的状态，不能表述为所有退出码都被改成 `0`。

**原因与定位：** `install/typo.bash:479` 保存失败状态后没有返回该状态，`install/typo.bash:557` 又把钩子插在已有 `PROMPT_COMMAND` 前。`install/typo.bash:524` 在执行旧 EXIT trap 之前先执行清理，覆盖了 `$?`。

现有 `internal/cmd/shell_integration_uninstall_test.go:261` 只确认原 EXIT trap 执行过，未验证其收到的状态。

**影响：** 依赖退出状态的提示符或退出处理会误判成功。

**建议及验收：** 在钩子链间保留并传递入口状态，补齐失败命令、失败退出和既有钩子组合测试。

### F05：损坏 JSON 的隔离备份名称可能碰撞

**触发条件：** 同一文件在同一秒内两次写入损坏内容，并分别触发加载隔离。

**复现与结果：** 连续生成两份不同损坏内容并执行 `typo config list`。两次均返回错误且声称已隔离，目录中却只剩一个 `config.json.corrupt-<timestamp>`，内容为第二份；第一份已被覆盖。

**原因与定位：** `internal/storage/files.go:87` 仅用秒级时间戳构造目标文件名，直接调用 `os.Rename`。本机 Unix 文件系统允许覆盖同名目标。现有 `TestQuarantineInvalidJSON` 只覆盖单次隔离。

**影响：** 在快速重复损坏场景中，隔离机制无法保留全部恢复证据。

**建议及验收：** 使用不会覆盖已有文件的唯一备份名或排他创建流程。验收要求快速重复隔离保留两份原始内容，并补充并发隔离场景。本次未在 Windows 文件系统复现。
